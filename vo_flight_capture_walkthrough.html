vo_flight_capture.py

從 visual_odometry.py 跟 live_vo_gps.py 衍生出來的全新腳本：換成水平視角 77 度的新鏡頭、拿掉中央裁切、只在起飛超過 40m 後才每 2 秒拍一張，並把每張照片存成一個帶有「真實 GPS vs VO 估算」比對欄位的檔名，降落後自動停止。這支程式只讀 Pixhawk 遙測，不會把 VO 位置寫回飛控。

01

新相機常數 — 為什麼要重算焦距、拿掉裁切

這支程式換了一顆水平視角 77 度的鏡頭，不再是舊魚眼鏡頭那樣邊緣嚴重畸變，所以裁切可以直接拿掉；但 config.py 裡的 FX_PIXELS／FY_PIXELS 是從舊鏡頭實測的地面涵蓋範圍反推出來的，套在新鏡頭上答案會整個錯，所以這支程式定義了自己的一組相機常數，完全不動 config.py（其他程式，例如 process_dji_sequence.py、recompute_vo_trajectory.py、dead_reckoning.py 的自我測試，還在用舊鏡頭的那組設定）。
模組常數（不是函式，程式一載入就算好）
設定
# ── New camera: 77-deg HORIZONTAL FOV, no fisheye crop ──────────────────────
# Only the horizontal FOV was specified, so this assumes square pixels
# (fx == fy in pixel units) and derives the focal length from a plain
# pinhole model rather than reusing config.py's footprint-derived
# FX_PIXELS/FY_PIXELS, which were empirically fit to the OLD ~166-deg
# fisheye lens and do not apply here.
IMAGE_WIDTH = 1280
IMAGE_HEIGHT = 720
CAMERA_HFOV_DEG = 77.0
FX_PIXELS = (IMAGE_WIDTH / 2.0) / math.tan(math.radians(CAMERA_HFOV_DEG / 2.0))
FY_PIXELS = FX_PIXELS  # square-pixel assumption -- see note above

# No AGL reading available yet (e.g. first Pixhawk read glitches) -- use the
# takeoff altitude itself as a fallback, since capture never starts below it.
FALLBACK_ALTITUDE_M = 40.0

用最單純的針孔相機模型反推焦距（像素）：fx = (影像寬度 ÷ 2) ÷ tan(水平視角 ÷ 2)。因為只知道「水平」視角是 77 度，沒有另外量垂直視角，這裡假設像素是正方形（fx = fy），用同一個焦距值去換算垂直方向的公尺數。以 1280×720 代入，算出來 FX_PIXELS = FY_PIXELS ≈ 804.6px。

FALLBACK_ALTITUDE_M 取代了原本 config.REFERENCE_ALTITUDE_M（60m，舊鏡頭的參考高度）當作「兩張照片都沒有可用高度時」的備援值，改用 40（跟起飛判斷用的高度門檻一致，因為這支程式本來就不會在 40m 以下開始拍照）。

假設：水平視角只給了一個數字

如果之後量出鏡頭實際的垂直視角，或有精確的校正參數，應該直接把 FY_PIXELS 改成量出來的值，不要繼續套用「正方形像素」這個假設 —— 目前這只是在沒有更多資訊時的合理猜測，不是校正過的鏡頭規格。

02

特徵比對＋位移換算 — 這次不做中央裁切

跟 visual_odometry.py 幾乎一模一樣的核心演算法：RANSAC 擬合、兩層信心把關的邏輯完全沒變，唯二的差別是不呼叫 _central_crop()，以及用上一段新算出來的相機常數，而不是 config.py 裡的舊常數。
_detect_and_match_full_frame(gray1, gray2)
核心
def _detect_and_match_full_frame(gray1, gray2):
    """Same as visual_odometry.detect_and_match(), minus the central crop --
    the 77-deg lens isn't expected to have the old lens's edge distortion,
    so the full frame is used directly."""
    detector, norm = vo._make_detector()
    kp1, des1 = detector.detectAndCompute(gray1, None)
    kp2, des2 = detector.detectAndCompute(gray2, None)
    if des1 is None or des2 is None or len(kp1) < 4 or len(kp2) < 4:
        return np.empty((0, 2)), np.empty((0, 2))

    bf = cv2.BFMatcher(norm)
    raw_matches = bf.knnMatch(des1, des2, k=2)
    good = [m for m, n in raw_matches if n is not None and m.distance < config.MATCH_RATIO * n.distance]

    pts1 = np.float32([kp1[m.queryIdx].pt for m in good])
    pts2 = np.float32([kp2[m.trainIdx].pt for m in good])
    return pts1, pts2

直接沿用 visual_odometry.py 的 _make_detector()（依 config.DETECTOR 決定用 SIFT 還是 ORB，這個設定跟相機鏡頭無關，所以不用重寫），對兩張完整原圖做 detectAndCompute()、knnMatch(k=2)、Lowe's ratio test。

跟原版 detect_and_match() 比起來，少了兩件事：沒有呼叫 _central_crop()，也沒有「把座標加回裁切偏移量」那一步 —— 因為根本沒裁切，偵測到的座標本來就已經是全圖座標，不需要再加回去。

_displacement_from_transform(M, altitude_m)
核心
def _displacement_from_transform(M, altitude_m):
    """Same math as visual_odometry.displacement_from_transform(), using
    this script's own IMAGE_WIDTH/HEIGHT/FX_PIXELS/FY_PIXELS."""
    a, b, tx = M[0]
    c, d, ty = M[1]
    scale = math.sqrt(a * a + c * c)
    theta_rad = math.atan2(c, a)

    cx, cy = IMAGE_WIDTH / 2.0, IMAGE_HEIGHT / 2.0
    center2 = np.array([a * cx + b * cy + tx, c * cx + d * cy + ty])
    apparent_flow = center2 - np.array([cx, cy])
    cam_shift_px = -apparent_flow

    gsd_x = altitude_m / FX_PIXELS
    gsd_y = altitude_m / FY_PIXELS
    dx_m = cam_shift_px[0] * gsd_x
    dy_m = cam_shift_px[1] * gsd_y

    return {
        'dx_m': dx_m,
        'dy_m': dy_m,
        'magnitude_m': math.hypot(dx_m, dy_m),
        'yaw_change_deg': -math.degrees(theta_rad),
        'scale': scale,
        'altitude_change_m': altitude_m * (1.0 / scale - 1.0) if scale > 0 else float('nan'),
    }

跟 visual_odometry.displacement_from_transform() 逐行一模一樣的數學：拆解相似變換矩陣 M 得到縮放量跟旋轉角、算「畫面中心點」看起來跑到哪去了、取負號還原成相機自己的位移方向、再用 GSD = 高度 ÷ 焦距 換算成公尺。差別只在 cx,cy 用的是這支程式自己的 IMAGE_WIDTH/IMAGE_HEIGHT，gsd_x,gsd_y 用的是上一段新算出來的 FX_PIXELS/FY_PIXELS。

為什麼直接照抄這段數學，不用重新驗證？

visual_odometry.py 裡這段公式已經用合成資料驗證過，誤差在 3 公分內（見 summary.md）——這是純幾何／三角函數的推導，跟鏡頭視角無關，只要 FX_PIXELS/FY_PIXELS 跟 IMAGE_WIDTH/IMAGE_HEIGHT 換成新鏡頭的正確數值，同一套公式就一樣成立。真正還沒驗證過的是「新鏡頭反推出來的 FX_PIXELS 準不準」，不是這段數學本身。

process_pair(gray1, gray2, alt1, alt2)
整合
def process_pair(gray1, gray2, alt1, alt2):
    """Full-frame, 77-deg-camera equivalent of
    visual_odometry.process_pair_arrays()."""
    pts1, pts2 = _detect_and_match_full_frame(gray1, gray2)
    M, inliers = vo.estimate_similarity(pts1, pts2)

    n_matches = len(pts1)
    n_inliers = int(inliers.sum()) if inliers is not None else 0
    result = {'n_matches': n_matches, 'n_inliers': n_inliers, 'ok': False, 'confident': False}
    if M is None or inliers is None or n_inliers < config.MIN_INLIERS:
        result['reason'] = 'too few inliers'
        return result

    altitude_m = (alt1 + alt2) / 2.0 if (alt1 and alt2) else (alt1 or alt2 or FALLBACK_ALTITUDE_M)
    result.update(_displacement_from_transform(M, altitude_m))
    result['ok'] = True
    result['altitude_used_m'] = altitude_m
    result['confident'] = (n_inliers / n_matches) >= config.MIN_INLIER_RATIO
    if not result['confident']:
        result['reason'] = 'low inlier ratio -- displacement UNTRUSTED'
    return result

把上面兩個函式接起來，並套用跟原版完全相同的兩層信心把關：estimate_similarity() 直接沿用 visual_odometry.py 的版本（RANSAC 擬合矩陣的邏輯，跟裁不裁切、哪台相機都無關）。

  • 第一層：n_inliers < config.MIN_INLIERS —— inlier 太少，直接判定失敗
  • 第二層：n_inliers / n_matches < config.MIN_INLIER_RATIO —— 比例太低，標成 confident=False，位移還是會回傳但不可信

這個函式在整個新程式的主迴圈裡，就是原版 visual_odometry.process_pair_arrays() 的角色 —— 讀記憶體裡的灰階陣列，不用先寫檔。

相機開啟與 Pixhawk 讀取 — 沿用 live_vo_gps.py

連 Pixhawk、讀 GPS／航向、開 CSI 相機的邏輯跟 live_vo_gps.py 完全一樣，這支程式直接 import 過來用，沒有重新寫一份。只有 open_camera() 因為要明確指定新相機的解析度，多包了一層。

沿用

這五個函式全部是直接從 live_vo_gps.py import 過來，本檔案裡沒有另外定義：

  • gstreamer_pipeline() —— 組出 Jetson CSI 相機的 GStreamer pipeline 字串，接受 width／height 參數，所以可以指定新相機的解析度
  • capture_gray() —— 從已開啟的相機讀一張影格，回傳彩色（存檔用）跟灰階（VO 用）兩份
  • connect_pixhawk(port, baud) —— 用 pymavlink 連線、等待 heartbeat、訂閱資料流
  • read_global_position(conn, timeout) —— 讀最新一筆 GLOBAL_POSITION_INT，回傳 (lat, lon, alt_msl, alt_agl)
  • read_heading(conn, timeout) —— 讀最新一筆 VFR_HUD 的真航向（度）
跟 live_vo_gps.py 的關鍵差異：完全不寫回 Pixhawk

live_vo_gps.py 除了讀，還會呼叫 gps_sim.send_gps_input() 把 VO 估算位置持續送回飛控當 GPS2。這支程式只 import 讀取用的函式，從頭到尾沒有 import 也沒有呼叫任何送出 GPS_INPUT 的函式 —— 純粹是資料紀錄工具，真正飛的還是靠真實 GPS。

open_camera(sensor_id)
相機
def open_camera(sensor_id):
    pipeline = gstreamer_pipeline(sensor_id=sensor_id, width=IMAGE_WIDTH, height=IMAGE_HEIGHT)
    cap = cv2.VideoCapture(pipeline, cv2.CAP_GSTREAMER)
    if not cap.isOpened():
        raise RuntimeError("Could not open CSI camera — check sensor connection / nvargus-daemon.")
    for _ in range(10):  # let exposure settle
        cap.read()
    return cap

跟 live_vo_gps.py 的 open_camera() 做一樣的事，但明確傳入 width=IMAGE_WIDTH, height=IMAGE_HEIGHT（這支程式自己的 1280×720 常數），而不是讓 gstreamer_pipeline() 偷偷套用它自己 config.IMAGE_WIDTH/IMAGE_HEIGHT 的預設值。這兩組數字現在剛好一樣（都是 1280×720），但故意寫死傳入是為了不要之後 config.py 為了舊鏡頭改了解析度，這支程式的相機開啟行為卻悄悄跟著變。

開機後先丟掉前 10 個影格，讓自動曝光穩定下來（跟 capture_sample.py 的作法一樣）。

04

起飛／降落判斷與整個飛行流程

這是這支程式跟 visual_odometry.py／live_vo_gps.py 最不一樣的地方：不是「餵幾張現成的照片」，也不是「開機就持續即時定位」，而是自己判斷「什麼時候該開始拍」「什麼時候該停」，並且把每一張照片存成一個帶有真實 GPS／VO 比對欄位的檔名。
wait_for_takeoff(conn, takeoff_altitude_m, poll_s=0.5)
流程控制
def wait_for_takeoff(conn, takeoff_altitude_m, poll_s=0.5):
    print(f"Waiting for relative altitude > {takeoff_altitude_m:.1f}m ...")
    last_print = 0.0
    while True:
        pos = read_global_position(conn, timeout=2.0)
        if pos is not None:
            alt_agl = pos[3]
            now = time.time()
            if now - last_print > 5.0:
                print(f"  current relative altitude: {alt_agl:.1f}m")
                last_print = now
            if alt_agl > takeoff_altitude_m:
                print(f"Takeoff altitude reached ({alt_agl:.1f}m). Starting capture.\n")
                return
        time.sleep(poll_s)

在正式開始拍照之前，先卡在這個迴圈裡，每 poll_s（預設 0.5 秒）讀一次 GLOBAL_POSITION_INT 的相對高度（AGL，離地高度），每 5 秒印一次目前高度讓操作者知道還在等。一旦 AGL 超過 --takeoff-altitude-m（預設 40m），就直接 return，回到 main() 繼續往下走。

為什麼用 AGL 不是 MSL？

「飛高於 40 公尺」指的是離地高度，跟起飛地點的海拔無關，所以這裡用 pos[3]（relative_alt，AGL）而不是 pos[2]（alt，MSL）。--land-altitude-m 的降落判斷（見第 10 段）用的是同一個 AGL 欄位，邏輯一致。

錨點讀取時間點 vs. 第一張照片時間點，中間有一段沒被追蹤到

錨點是「程式一啟動」就讀的（通常在地面），但要等到 AGL 超過 40m 才開始拍第一張照片。這中間的爬升過程完全沒有任何 VO 影像被拿來計算位移，tracker 的位置在第一張照片拍下之前都還停在錨點原地。第 9、10 段會看到：這會讓第一張照片的 real_vo_diff_m 欄位是一個真實存在、而不是 0 的數字 —— 這是設計上的取捨，不是 bug。

每一輪迴圈：先用 capture_gray() 拍一張（彩色存檔用、灰階算圖用），再用 read_global_position(timeout=0.5) 讀「這一瞬間」的真實 GPS —— 這組數字只會寫進檔名做事後比對，完全不會餵進 VO 計算，跟 photo_obtained/ 舊測試照片檔名裡的 GPS 是同一種「僅供驗證」的角色。如果這次讀取失敗（real_pos is None），就退回用錨點座標／上一張的 AGL 頂著，不讓程式當掉。

接著是這支程式的核心分支：

  • 第一張照片（prev_gray is None）：沒有前一張可以比對，直接給一組「什麼都沒發生」的空結果（matches=inliers=0、位移全部是 0），tracker 這時仍然停在錨點
  • 第二張照片開始：呼叫第 4 段的 process_pair() 算這一段的位移，再丟給 tracker.apply_leg() 往前推進。apply_leg() 回傳的 vn／ve（公尺/秒）乘回 dt_s（這一輪實際經過的秒數），還原成這一段的北／東位移（公尺），當作檔名裡的 move_x／move_y；move_z 直接拿 process_pair() 算出來的高度變化
  • 只有 r['ok'] 為真（就算是 LOW-CONFIDENCE 也算）的那一段，才會累加進 agg_distance_m（總飛行里程）—— 這跟 dead_reckoning.PositionTracker.apply_leg() 本身「只要 ok 就會移動位置、信心只影響 hacc 成長速度」的邏輯是一致的
vo_move_x／y／z 是「世界座標」不是「影像座標」

跟 visual_odometry.py 印出來的 dx_m／dy_m（相機自己視角裡的右／下方向）不一樣，這裡的 move_x／move_y 已經被 tracker 內部依照累積航向角旋轉成北／東方向，move_z 是高度變化（正值＝爬升）。這樣檔名裡的位移量才能直接跟 real_lat/lon/height、vo_lat/lon/height 用同一個座標系統對照。

            fname = (
                f"VO_{ts}_{real_lat:.7f}_{real_lon:.7f}_{real_alt_msl:.2f}_"
                f"{tracker.lat:.7f}_{tracker.lon:.7f}_{tracker.alt_m:.2f}_{diff_m:.2f}_"
                f"{move_x:.2f}_{move_y:.2f}_{move_z:.2f}_"
                f"{r['n_matches']}_{r['n_inliers']}_{agg_distance_m:.2f}.png"
            )
            cv2.imwrite(os.path.join(out_dir, fname), frame)

            prev_gray, prev_time, prev_alt_agl = gray, now, cur_alt_agl

            if cur_alt_agl < args.land_altitude_m:
                print(f"\nRelative altitude {cur_alt_agl:.1f}m < land threshold "
                      f"{args.land_altitude_m:.1f}m — landed, stopping.")
                has_landed = True
                continue

            elapsed = time.time() - now
            time.sleep(max(0.0, args.interval - elapsed))

用 vo.haversine_m()（直接沿用 visual_odometry.py 的大圓距離公式）算出「這一瞬間的真實 GPS」跟「tracker 目前估算的位置」之間的水平距離，當作 diff_m（檔名裡的 Real_VO_GPS_difference）。

接著照著要求的欄位順序組出檔名（時間戳記 yyyymmddhhmmss、真實經緯高、VO 經緯高、差距、北／東／高度位移、matches、inliers、累積飛行距離），用 cv2.imwrite() 把彩色影格存進 photo_obtained/。

存完檔才把這張的灰階影格／時間／AGL 記成 prev_*，供下一輪當作「前一張」；然後檢查降落判斷：只要這一瞬間的 AGL 掉到 --land-altitude-m（預設 2m）以下，就把 has_landed 設成 True，讓 while not has_landed 迴圈在下一輪開頭自然結束。最後用 time.sleep() 補齊到剛好 --interval 秒，扣掉這一輪處理已經花掉的時間，避免每輪之間的間隔越拖越長。

降落判斷是單純的高度門檻，沒有防抖動

只要 AGL 曾經一度低於 --land-altitude-m 就會停止，不會判斷「是不是真的已經降落並斷電」，也不像 dead_reckoning.py 那樣有 hacc 之類的信心概念。如果飛行過程中在低空短暫掠過這個高度（例如起飛前的地面效應量測雜訊、或刻意貼地飛行），程式會提早結束。目前門檻預設 2m，可以用 --land-altitude-m 調整。

整個拍照迴圈包在 try/except/finally 裡：Ctrl+C（KeyboardInterrupt）可以隨時手動中斷，不會是唯一的停止方式（正常情況下是第 10 段的降落高度判斷讓迴圈自然跳出）；不論怎麼結束，finally 都會呼叫 cap.release() 把相機釋放掉。

最後印一行總結：總共拍了幾張、tracker.legs_since_anchor（套用了幾段有效的 VO leg）、累積飛行距離、最終 VO 估算位置，以及最終的 hacc_m（水平精度信心值，越大代表跟真實位置可能差越多）。
