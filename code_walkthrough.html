01

輸入處理 — 決定拍照順序、讀高度、讀驗證用 GPS

這一段完全不碰影像內容，只處理檔案本身：哪張先拍、每張的高度是多少、檔名裡有沒有可以拿來驗證答案的真實 GPS。
list_images(paths)
入口
def list_images(paths):
    """Expand directories, then order frames by capture time (mtime).

    On the real drone, feed this script the photos in capture order (or
    give filenames that sort chronologically); mtime is only a convenience
    for this offline test set, since the GPS coordinates baked into these
    filenames are NOT in flight order.
    """
    files = []
    for p in paths:
        if os.path.isdir(p):
            for name in os.listdir(p):
                if name.lower().endswith(('.png', '.jpg', '.jpeg')):
                    files.append(os.path.join(p, name))
        else:
            files.append(p)
    files.sort(key=os.path.getmtime)
    return files

把傳進來的路徑（可能是資料夾、也可能是一張張照片）展開成一份檔案清單，並依照檔案的修改時間（mtime）排序，當作拍攝的時間先後順序。

真正飛行時，因為是「邊拍邊處理」，順序自然就是對的；這裡用 mtime 排序，是因為離線測試用的 photo_obtained/ 檔名裡帶的是 GPS 座標而不是時間戳記，沒辦法直接從檔名看出拍攝順序。

注意

這是 3 張照片唯一用來決定「誰先誰後」的依據。如果照片是用 cp 複製過去、或是從別的地方下載下來的，mtime 可能會被重設成複製當下的時間，順序就會跟著錯掉。

parse_altitude_m(path)
輸入
def parse_altitude_m(path):
    m = FILENAME_ALT_RE.search(os.path.basename(path))
    return float(m.group(1)) if m else None

用正規表示式從檔名尾端抓出高度，例如 ..._60.0m.png 會抓出 60.0。如果檔名不符合這個格式就回傳 None，之後會用 config.REFERENCE_ALTITUDE_M（預設高度）頂替。

parse_gps(path)
輸入
def parse_gps(path):
    """Ground-truth GPS from the filename, if present. VALIDATION ONLY —
    never fed into the displacement estimate itself."""
    m = FILENAME_GPS_RE.match(os.path.basename(path))
    if not m:
        return None
    return float(m.group(1)), float(m.group(2))

從檔名開頭抓出真實 GPS 座標（例如 25.0432642_121.4743882-...）。這個函式抓到的座標只會拿來跟演算法算出來的位移做事後比對，絕對不會被拿去當作演算法的輸入 —— 不然就是「作弊」，用答案去驗證答案。

haversine_m(lat1, lon1, lat2, lon2)
輸入
def haversine_m(lat1, lon1, lat2, lon2):
    R = 6371000.0
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dphi = math.radians(lat2 - lat1)
    dlmb = math.radians(lon2 - lon1)
    a = math.sin(dphi / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dlmb / 2) ** 2
    return 2 * R * math.asin(math.sqrt(a))

標準的大圓距離（Haversine）公式：地球是球面，兩個經緯度座標之間的實際距離不能直接用平面畢氏定理算，要用這個公式球面三角換算。這裡拿來把兩張照片檔名裡的真實 GPS 換算成「地面實際距離」，當作驗證用的正確答案。

02

特徵比對 — 兩張照片裡，哪些點其實是同一個地方？

這是整支程式最核心的電腦視覺部分：在兩張照片裡各自找出「好認的點」（特徵點），然後把「同一個地方」在兩張照片裡的位置配對起來。
_central_crop(gray)
前處理
def _central_crop(gray):
    h, w = gray.shape[:2]
    f = config.CENTRAL_CROP_FRACTION
    if f >= 1.0:
        return gray, (0, 0)
    cw, ch = int(w * f), int(h * f)
    x0, y0 = (w - cw) // 2, (h - ch) // 2
    return gray[y0:y0 + ch, x0:x0 + cw], (x0, y0)

只取影像中央的一塊（預設 config.CENTRAL_CROP_FRACTION = 0.8，即中央 80%），把邊緣裁掉。這台 Jetson 用的 IMX219 鏡頭視角偏廣，靠近邊緣的地方會有明顯的魚眼變形（畫面裡的跑道、球場邊線靠近邊框會彎曲），這種變形不是單純的「旋轉＋縮放＋平移」能描述的，會讓後面的數學模型算錯，所以乾脆不用邊緣的點。

_make_detector()
前處理
def _make_detector():
    if config.DETECTOR == 'orb':
        return cv2.ORB_create(nfeatures=config.ORB_N_FEATURES), cv2.NORM_HAMMING
    return cv2.SIFT_create(nfeatures=config.SIFT_N_FEATURES), cv2.NORM_L2

依照 config.DETECTOR 的設定，回傳 SIFT 或 ORB 其中一種「特徵偵測器」物件，以及對應要用哪種方式比較兩個特徵描述子的距離（SIFT 用 NORM_L2 歐氏距離，ORB 用 NORM_HAMMING 因為它的描述子是二進位的）。

detect_and_match(gray1, gray2)
核心
def detect_and_match(gray1, gray2):
    """Returns matched point pairs (Nx2 arrays, in ORIGINAL full-frame pixel
    coordinates) after Lowe's ratio test."""
    crop1, off1 = _central_crop(gray1)
    crop2, off2 = _central_crop(gray2)

    detector, norm = _make_detector()
    kp1, des1 = detector.detectAndCompute(crop1, None)
    kp2, des2 = detector.detectAndCompute(crop2, None)
    if des1 is None or des2 is None or len(kp1) < 4 or len(kp2) < 4:
        return np.empty((0, 2)), np.empty((0, 2))

    bf = cv2.BFMatcher(norm)
    raw_matches = bf.knnMatch(des1, des2, k=2)
    good = [m for m, n in raw_matches if n is not None and m.distance < config.MATCH_RATIO * n.distance]

    pts1 = np.float32([kp1[m.queryIdx].pt for m in good])
    pts2 = np.float32([kp2[m.trainIdx].pt for m in good])
    if len(pts1):
        pts1 += np.array(off1)
        pts2 += np.array(off2)
    return pts1, pts2

這個函式做了四件事：

  • 對兩張照片各自做 _central_crop()
  • 用偵測器的 detectAndCompute() 在兩張照片裡各自找出一堆「特徵點＋描述子」——特徵點是「這裡有個好認的角落／紋理」的位置，描述子是一串數字，用來描述這個點附近長什麼樣子
  • 用 cv2.BFMatcher 的 knnMatch(..., k=2)，幫第一張照片裡每個特徵點，在第二張照片裡找出「長得最像」跟「第二像」的兩個候選
  • 套 Lowe's ratio test：只留下「最像的候選明顯比第二像的候選更像」的配對

回傳的座標最後會加回裁切掉的偏移量（off1／off2），所以回傳的還是「整張原圖」的像素座標，不是裁切後的座標。

概念：為什麼要比對「最像」和「第二像」兩個候選？

如果一張照片裡有大片草地或跑道這種重複紋理，某個點在另一張照片裡可能會有好幾個地方看起來都差不多像。這種情況下「最像」的那個很可能只是運氣好，不能相信。Lowe's ratio test 的邏輯是：只有當「最像」的候選遠遠拋開「第二像」的候選（差距超過 config.MATCH_RATIO = 0.75），才算是一個夠可靠、不含糊的配對。

estimate_similarity(pts1, pts2)
核心
def estimate_similarity(pts1, pts2):
    """Fit pts2 ~= s*R*pts1 + t via RANSAC. Returns (M 2x3, inlier_mask)."""
    if len(pts1) < 4:
        return None, None
    M, inliers = cv2.estimateAffinePartial2D(
        pts1, pts2,
        method=cv2.RANSAC,
        ransacReprojThreshold=config.RANSAC_REPROJ_THRESHOLD_PX,
        confidence=0.99,
    )
    return M, inliers

拿上一步配對出來的點對，用 cv2.estimateAffinePartial2D() 搭配 RANSAC 演算法，擬合出一個 2×3 的矩陣 M —— 這個矩陣描述「一個統一的旋轉＋縮放＋平移」，能把第一張照片裡的點盡量對應到第二張照片裡配對到的位置。回傳的 inliers 是一個布林陣列，標記哪些配對點真的符合這個矩陣（其餘的視為誤配，直接忽略）。

概念：RANSAC 在解決什麼問題？

前一步的配對裡，難免混著一些錯的配對（誤配）。RANSAC 的做法是：隨機抽幾個點算出一個候選模型，看看有多少其他點也符合這個模型，重複很多次，最後選「支持者最多」的那個模型。這樣就算配對裡混了不少雜訊，只要「正確的配對」佔多數，RANSAC 通常還是能找出正確的整體變換，並順便標出哪些點是雜訊（outlier）。

03

像素位移 → 實際公尺

上一段只算出「影像座標系裡」的一個變換矩陣，完全不知道公尺、公分這些真實世界的單位。這一段負責把它換算成「相機真的移動了幾公尺」。
displacement_from_transform(M, altitude_m)
核心
def displacement_from_transform(M, altitude_m):
    """Convert a pts1->pts2 similarity transform into the camera's own
    metric displacement, expressed in image axes (x=image-right, y=image-down)
    as they appeared in frame 1.

    Reasoning: a stationary ground feature's apparent position shifts
    OPPOSITE to the camera's own motion (walk forward, the ground appears to
    flow backward under you). So we transform the image center through M to
    see how a center-fixed feature appears to move, then negate that to get
    the camera's own translation.
    """
    a, b, tx = M[0]
    c, d, ty = M[1]
    scale = math.sqrt(a * a + c * c)
    theta_rad = math.atan2(c, a)  # apparent rotation of the world in-image

    cx, cy = config.IMAGE_WIDTH / 2.0, config.IMAGE_HEIGHT / 2.0
    center2 = np.array([a * cx + b * cy + tx, c * cx + d * cy + ty])
    apparent_flow = center2 - np.array([cx, cy])
    cam_shift_px = -apparent_flow  # camera's own displacement, in pixels

    gsd_x = altitude_m / config.FX_PIXELS
    gsd_y = altitude_m / config.FY_PIXELS
    dx_m = cam_shift_px[0] * gsd_x
    dy_m = cam_shift_px[1] * gsd_y

    return {
        'dx_m': dx_m,           # + = camera moved toward image-right
        'dy_m': dy_m,           # + = camera moved toward image-down
        'magnitude_m': math.hypot(dx_m, dy_m),
        'yaw_change_deg': -math.degrees(theta_rad),  # camera's own yaw change
        'scale': scale,         # >1: frame2 zoomed in => flew lower
        'altitude_change_m': altitude_m * (1.0 / scale - 1.0) if scale > 0 else float('nan'),
    }

這是整支程式數學味最重的一個函式，拆解成幾步：

  • 拆解矩陣：M 的四個係數 a,b,c,d 可以拆出 scale（縮放倍率）跟 theta_rad（世界看起來轉了幾度）
  • 算「畫面中心點」跑到哪裡去了：把影像正中央的座標 (cx, cy) 代入 M，看看它在第二張照片裡對應到哪裡，兩者的差 apparent_flow 就是「畫面中央這個點看起來移動了多少」
  • 反過來，取負號：地面上固定不動的東西，看起來會往相機移動的反方向流動（想像你往前走，地面看起來往後退）。所以要把 apparent_flow 取負號，才是相機自己真正移動的方向
  • 換算成公尺：用 GSD = 高度 ÷ 焦距(像素) 算出「每個像素代表多少公尺」，乘上剛剛算出的像素位移

最後回傳的字典裡，dx_m／dy_m 是位移分量，yaw_change_deg 是相機自己轉了幾度，scale 則反過來能推算出高度變化了多少（飛高了會「縮小」、飛低了會「放大」）。

這段數學已經用合成資料驗證過

拿一張真實照片，用已知的位移／旋轉量刻意「合成」出第二張照片，再丟回這個函式反推，結果跟已知答案誤差在 3 公分內 —— 代表這個換算公式本身是對的，準確度的瓶頸在特徵比對階段，不是這裡的數學。

04

整個序列的處理 — 把每一對照片串成一條軌跡

前面三段都只處理「一對」照片。這一段把它們組合起來，處理一整串照片，並且加上「這個結果可不可信」的把關機制。
process_pair(path1, path2, alt1, alt2)
整合
def process_pair(path1, path2, alt1, alt2):
    img1 = cv2.imread(path1, cv2.IMREAD_GRAYSCALE)
    img2 = cv2.imread(path2, cv2.IMREAD_GRAYSCALE)
    if img1 is None or img2 is None:
        raise FileNotFoundError(f"could not read {path1} or {path2}")
    result = process_pair_arrays(img1, img2, alt1, alt2)
    result['from'], result['to'] = path1, path2
    return result

從硬碟讀兩張照片（轉灰階），檢查讀取成功後，直接呼叫 process_pair_arrays() 做真正的運算，只是多補上 from／to 兩個檔名欄位方便後面印報告。這是給「批次處理資料夾」用的入口。

process_pair_arrays(gray1, gray2, alt1, alt2)
整合
def process_pair_arrays(gray1, gray2, alt1, alt2):
    """Same as process_pair(), but on already-decoded grayscale arrays —
    used by the live capture loop, which never round-trips frames to disk."""
    pts1, pts2 = detect_and_match(gray1, gray2)
    M, inliers = estimate_similarity(pts1, pts2)

    n_matches = len(pts1)
    n_inliers = int(inliers.sum()) if inliers is not None else 0
    result = {
        'n_matches': n_matches,
        'n_inliers': n_inliers,
        'ok': False,
        'confident': False,
    }
    if M is None or inliers is None or n_inliers < config.MIN_INLIERS:
        result['reason'] = 'too few inliers'
        return result

    altitude_m = (alt1 + alt2) / 2.0 if (alt1 and alt2) else (alt1 or alt2 or config.REFERENCE_ALTITUDE_M)
    disp = displacement_from_transform(M, altitude_m)
    result.update(disp)
    result['ok'] = True
    result['altitude_used_m'] = altitude_m
    result['confident'] = (n_inliers / n_matches) >= config.MIN_INLIER_RATIO
    if not result['confident']:
        result['reason'] = 'low inlier ratio (likely low image overlap or repetitive texture) -- displacement below is UNTRUSTED'
    return result

跟 process_pair() 做一樣的事，差別是直接吃「已經讀進記憶體的影像陣列」，不用先寫檔再讀檔——這是專門給 live_vo_gps.py 即時拍照迴圈用的版本，省掉每一張都要存檔再讀檔的開銷。

核心邏輯是兩層信心把關：

  • 第一層：n_inliers < config.MIN_INLIERS —— inlier 數量太少，代表 RANSAC 幾乎找不到一致的變換，直接判定失敗（ok=False）
  • 第二層：n_inliers / n_matches < config.MIN_INLIER_RATIO —— 就算 inlier 數量夠多，但佔全部配對的比例太低，代表可能是重複紋理造成的巧合，標記成 confident=False（結果還是會回傳，但標成不可信）

這正是我們拿 photo_obtained/ 那 3 張照片實測時，兩段位移都被標成 LOW-CONFIDENCE 的原因——兩張照片之間距離太遠、重疊區域太小。

run(image_paths, altitudes=None)
整合
def run(image_paths, altitudes=None):
    frames = list_images(image_paths)
    if len(frames) < 2:
        raise SystemExit("need at least 2 images")

    if altitudes is None:
        altitudes = [parse_altitude_m(f) for f in frames]

    results = []
    traj = [(0.0, 0.0)]
    heading_deg = 0.0  # cumulative estimated yaw relative to frame 0

    for i in range(len(frames) - 1):
        r = process_pair(frames[i], frames[i + 1], altitudes[i], altitudes[i + 1])
        results.append(r)
        if r['ok'] and r['confident']:
            heading_deg += r['yaw_change_deg']
            th = math.radians(heading_deg)
            # rotate this leg's image-frame displacement into frame-0's reference frame
            dx, dy = r['dx_m'], r['dy_m']
            wx = dx * math.cos(th) - dy * math.sin(th)
            wy = dx * math.sin(th) + dy * math.cos(th)
            px, py = traj[-1]
            traj.append((px + wx, py + wy))
        else:
            traj.append(traj[-1])

    return frames, results, traj

對一整個序列跑迴圈，每一段都呼叫 process_pair()，然後做軌跡累加：

  • 維護一個 heading_deg，每處理完一段有信心的結果，就把這段的 yaw_change_deg 累加進去 —— 代表「相對於第 0 張照片，目前轉了多少角度」
  • 用這個累積角度，把這一段在「拍攝當下影像座標系」裡的位移 (dx_m, dy_m) 旋轉到「第 0 張照片」的參考座標系裡，再加到目前的累積位置上
  • 如果這一段失敗或信心不足，位置原地不動，直接沿用上一步的座標

這就是為什麼旋轉要先做——如果拍照途中相機轉了方向，後面的位移量必須先「轉回」統一的參考方向，才能正確疊加，不然軌跡的形狀會整個歪掉。

CLI — 指令列進入點

使用者實際打指令執行這支程式時，最先跑到的地方。負責解析參數、呼叫上面整套邏輯、把結果格式化印出來。
main()
入口
def main():
    ap = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    ap.add_argument('paths', nargs='+', help='image files and/or a directory of images')
    ap.add_argument('--altitude', help='comma-separated altitude (m) per frame, overrides filename parsing')
    args = ap.parse_args()

    altitudes = None
    if args.altitude:
        altitudes = [float(x) for x in args.altitude.split(',')]

    frames, results, traj = run(args.paths, altitudes)

    print(f"Sequence ({len(frames)} frames, ordered by capture time):")
    for f in frames:
        print(f"  {f}")
    print()

    for r in results:
        name1, name2 = os.path.basename(r['from']), os.path.basename(r['to'])
        if not r['ok']:
            print(f"[FAIL] {name1} -> {name2}: {r['n_inliers']}/{r['n_matches']} inliers "
                  f"-- {r.get('reason', 'unknown')}")
            continue
        tag = "[OK]  " if r['confident'] else "[LOW-CONFIDENCE]"
        print(f"{tag} {name1} -> {name2}")
        if not r['confident']:
            print(f"       WARNING: {r['reason']}")
        print(f"       matches={r['n_matches']} inliers={r['n_inliers']} altitude_used={r['altitude_used_m']:.1f}m")
        print(f"       displacement: dx={r['dx_m']:+.2f}m dy={r['dy_m']:+.2f}m "
              f"magnitude={r['magnitude_m']:.2f}m")
        print(f"       yaw_change={r['yaw_change_deg']:+.2f}deg altitude_change={r['altitude_change_m']:+.2f}m")

        gps1, gps2 = parse_gps(r['from']), parse_gps(r['to'])
        if gps1 and gps2:
            truth_m = haversine_m(gps1[0], gps1[1], gps2[0], gps2[1])
            err = r['magnitude_m'] - truth_m
            print(f"       ground truth (GPS in filename, validation only): {truth_m:.2f}m "
                  f"(error {err:+.2f}m, {abs(err)/truth_m*100:.0f}%)")
        print()

    print("Estimated trajectory (meters, frame-0 reference, x=image-right/y=image-down axes):")
    for f, (x, y) in zip(frames, traj):
        print(f"  {os.path.basename(f):55s} ({x:+7.2f}, {y:+7.2f})")

用 argparse 解析指令列參數（照片路徑、可選的 --altitude），呼叫 run() 拿到整個序列的結果，然後逐段印出：

  • [FAIL] —— inlier 太少，完全沒有可信的變換
  • [LOW-CONFIDENCE] —— 有算出位移，但 inlier 比例不夠，標成不可信
  • [OK] —— 有信心的結果

如果檔名裡剛好帶有真實 GPS（parse_gps() 抓得到），還會額外印出真實距離跟誤差百分比，方便對照。最後印出整段累積軌跡表。
